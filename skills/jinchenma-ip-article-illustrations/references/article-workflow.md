# 文章配图工作流

## 输入

接受以下输入：

- 用户直接粘贴的一段话或完整文章。
- 本地 Markdown、纯文本或可读取的文档路径。
- 用户提供的网页文章链接。
- 单个观点、论断或社交媒体帖子。
- 用户提供的产品界面、操作过程、运行结果或对话截图，以及每张截图要证明的内容。

读取完整输入后直接进入内部规划和图片生成。对于本地文件读取全部正文；对于网页链接获取正文内容；无法访问完整内容时说明缺口，不根据标题单独推测，也不凭不完整内容生图。

用户指定数量时遵循指定数量，除非内容明显不足以支撑；此时说明原因并使用更少图片。用户没有明确数量时按内容密度决定。

输入包含截图时，先判断截图是否能证明关键能力、操作位置或真实结果。基础状态能用一句话讲清楚时不选；被选中的截图进入 `screenshot-ip-mode.md`，正文插图按 `illustration-style.md` 选择画风。同一篇文章可以同时包含两种模式，但每张图只使用一种模式。

## 决定图片数量

按内容密度判断，字符数只作参考：

- 单个观点或 500 字以内：1 张。
- 约 500—1500 字：1—3 张。
- 约 1500—3500 字：3—5 张。
- 约 3500 字以上：4—8 张。

长文默认不超过 8 张。不要按章节平均分配，也不要为了达到区间上限制造重复图片。

## 选择认知锚点

优先选择：

- 全文总判断或头图命题。
- 读者容易误解的关键机制。
- 前后逻辑发生变化的认知转折。
- 两个概念之间的冲突、脱钩或反直觉关系。
- 能够转化为行动的结论。

合并语义重复的章节，并结合文章已有图片判断还缺什么解释。为每张候选图用一句话明确读者看完应理解什么；只是装饰、补充背景或重复已有图意时不新增。具体例子能帮助读者理解关键机制时可以选用，不因它是举例而排除。

## 设计内部图片方案

每张图写清：

- 序号与简短英文主题 slug。
- 建议放置位置。
- 图的主题。
- 核心意思，以及需要消除的误解或解释的关系。
- 可见场景/关系；具体表达方式和构图限制按本次选定风格包。
- 当前 IP 角色的职责、尺度、动作和情绪。
- 1—3 个主要物件。
- 必须准确呈现的短文字；语言跟随原文，给关键标签留出足够的字号与空间。

截图 IP 讲解图改为写清：

- 原截图要证明的能力或结果。
- 必须完整保留的界面区域和已有标注。
- 当前 IP 站在左下角还是右下角，以及人物尺度。
- 人物朝向、手势和需要指向的具体位置。
- 不得遮挡的文字、数据、按钮和操作路径。

图片方案只用于内部生成，不需要先向用户输出，也不等待二次确认。

## 组装生成提示

文章插图的提示明确包含：

1. 16:9 横版文章插图。
2. 当前 IP 包的三视图和角色规范；说明三视图是同一角色的三个角度。
3. 当前图片的文章意思、可见场景/关系和角色职责；具体构图按选定风格包。
4. 选定风格包的规范、提示模板与可选配色，不加载另一套画风规则。
5. 角色占比、动作和适配当前内容的情绪。
6. 1—3 个主要物件。
7. 必须逐字准确呈现的短文字及其语言，关键文字在正文内嵌尺寸下清楚可读，不靠缩小字号容纳更多内容。
8. 排除与核心意思无关的物件、装饰和说明；其他构图限制按所选风格包执行。

只从当前包读取人物身份。不要在自定义包提示中加入内置默认包的任何人物身份、服装、配件或稳定色规则。

截图 IP 讲解图的提示按 `screenshot-ip-mode.md` 组装，必须把原截图设为受保护的编辑目标，把当前 IP 三视图设为人物参考。不要把截图内容改绘成漫画，也不要让人物遮挡界面重点。

## 生成与检查

1. 每张图分别调用图像生成工具。
2. 不用一张拼图代替多张独立图片。
3. 检查画面是否准确解释预定意思，主要动作与关系是否符合正文，没有增加未经正文支持的结论。
4. 检查短文字是否逐字准确，并在文章常规显示尺寸下直接可读；字太小时优先删减非必要标签、缩短说明或调整布局，为关键文字放大字号，详细解释留在正文。文字错误时优先局部修正，错误较多时减少文字并重新生成。
5. 检查人物是否与当前包的三视图和角色规范一致。
6. 检查人物表情、尺度和动作是否适配当前内容。
7. 检查主要意思、场景/关系与必要物件是否清楚，是否满足选定风格包。
8. 按选定风格检查背景、留白、材质、光影和正文显示尺寸下的可读性；可将图片缩至约 400 像素宽检查关键文字和动作，不只看原图。
9. 每次迭代只修正一个主要问题，避免无关部分随之漂移。

截图 IP 讲解图额外检查：原界面有没有被重绘或改字、人物是否从合适的底角进入、指向动作是否准确、关键内容是否完整可读。任何一项失败时只修正该问题，不接受以“更有设计感”为理由改变截图事实。

如果宿主没有图像生成能力，输出每张图的完整可执行生成提示、当前包参考路径和保存计划，并明确标注图片尚未生成。

## 确定文章 slug

- 本地文章文件优先使用不含扩展名的文件名。
- 粘贴文字或网页优先使用标题；没有标题时根据核心主题生成。
- 规范化为简短英文小写 kebab-case，只使用字母、数字和连字符。
- 无法可靠翻译时使用稳定的通用 slug，例如 `article-topic`，不要把私人路径拼入名称。

## 选择输出根目录

在实际生成和保存图片前创建目录。

1. 优先识别宿主提供的当前项目或工作区根目录。
2. 宿主没有明确根目录时，可使用当前任务所在 Git 仓库根目录。
3. 确认根目录存在、可写，并且宿主沙箱允许写入。
4. 满足条件时使用 `<project-root>/.jinchenma-assets/<article-slug>/`。
5. 没有可识别项目根目录、项目不可写或沙箱禁止写入时，使用 `~/.jinchenma-assets/<article-slug>/`。
6. 用户明确指定其他输出目录时遵循用户选择，并继续应用非覆盖规则。

`.jinchenma-assets/` 只保存生成的文章插图，不保存 Builder 三视图、IP 包、原始照片或文章副本。

## 文件命名与非覆盖

使用两位数字序号和简短英文主题命名：

```text
01-disappearing-path.png
02-value-shift.png
03-portable-assets.png
```

保存前检查完整目标路径：

- 目标不存在时使用原名。
- 目标已存在时不要覆盖，依次尝试 `-v2`、`-v3`、`-v4`，直到找到未使用的名称。
- 修订某一张图时只为该图创建新版本，不改写其他图片。
- 最终回复始终报告实际保存的绝对路径。

## 交付与放置说明

默认将输入文章视为只读，不向原文插入图片、链接、Embed 或占位符。

最终回复按图片顺序报告：

- 图片用途和对应核心观点。
- 最终绝对路径。
- 建议插入位置，优先使用可直接定位的表述，例如“放在『某段末句』之后”或“放在『某标题』之前”。

保持最终回复简短，不重复完整图片方案或生成提示词。

用户只说“告诉我放哪里”“调整最终输出”或类似表达时，只调整文字交付，不修改文章文件。只有用户明确要求“把图片链接写入文章文件”“直接嵌入正文”时，才修改输入文章，并使用最终实际路径。
